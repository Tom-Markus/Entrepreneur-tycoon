# V2 — Comptes, sauvegarde cloud, classement mondial et carte

Ce document décrit l'architecture visée pour la V2. **Rien n'est implémenté**,
mais la V1 a été construite pour ne pas bloquer cette évolution.

## 1. Ce que la V1 prépare déjà

| Besoin V2 | Préparé en V1 |
|---|---|
| Rejouer une partie côté serveur | Moteur **déterministe** (`tick(state, dt, rng)`, RNG à graine dont l'état est sauvegardé) ; chaque décision passe par `applyAction` et est journalisée dans `state.actionLog` avec son jour. Test `rejeu : seed + journal d'actions reproduit la partie`. |
| Sauvegarde cloud | Interface `SaveAdapter` asynchrone (`save/load/list/delete/export/import`). Il suffit d'écrire un `CloudSaveAdapter` ; l'UI n'en sait rien. |
| Classement | `computeScore(state)` pure, versionnée (`SCORE_VERSION`), documentée dans `src/engine/score.js`. |
| Identité de partie | `state.meta.gameId` (UUID généré par l'UI), `seed`, `createdAt`, `saveVersion`. |
| Évolution du format | `migrations.js` (chaîne de migrations testée). |
| Séparation stricte | Le moteur n'a aucune dépendance au DOM/localStorage/temps réel : il peut tourner tel quel dans une Cloud Function / Edge Function (Node ou Deno). |

## 2. Architecture visée

Deux options raisonnables ; **recommandation : Supabase** (PostgreSQL + Auth +
Edge Functions en Deno, qui exécutent nos modules ES sans modification, et
politiques RLS pour la sécurité).

```
Navigateur (V1 actuelle)
  ├─ ui/            → bouton « Se connecter avec Google », onglet Classement, carte
  ├─ storage/CloudSaveAdapter.js  (implémente SaveAdapter via l'API Supabase)
  └─ engine/        (inchangé)

Supabase
  ├─ Auth : fournisseur Google (OAuth)
  ├─ Tables : profiles, saves, runs, leaderboard
  ├─ Storage : (optionnel) exports JSON volumineux
  └─ Edge Function « verify-run » : importe src/engine/ et rejoue la partie
```

Alternative Firebase : Auth Google + Firestore + Cloud Functions (Node 22, nos
modules ES fonctionnent aussi). Moins naturel pour les requêtes de classement
(tri, filtres par secteur/difficulté), d'où la préférence pour PostgreSQL.

### Tables (PostgreSQL)

```sql
profiles(id uuid pk = auth.uid, pseudo text unique, country text, city text,
         lat numeric(6,3), lng numeric(6,3), show_on_map bool default false, created_at timestamptz)

saves(id uuid pk, user_id uuid fk, slot text, game_id uuid, save_version int,
      summary jsonb, state jsonb, updated_at timestamptz)        -- RLS : user_id = auth.uid()

runs(id uuid pk, user_id uuid fk, game_id uuid unique, seed text, options jsonb,
     action_log jsonb, engine_version text, claimed_score int, verified_score int,
     verified bool, status text, days int, submitted_at timestamptz)

leaderboard (vue matérialisée) : meilleur verified_score par (user, secteur, difficulté)
```

### Flux de sauvegarde cloud
1. `CloudSaveAdapter.save(slot, state)` → `upsert` dans `saves` (même enveloppe
   JSON qu'en local : `format`, `saveVersion`, `summary`, `state`).
2. Synchronisation : la sauvegarde la plus récente (`updated_at`) gagne ; en cas
   de conflit, proposer les deux au joueur.
3. Hors-ligne : continuer en `LocalStorageAdapter` et pousser plus tard.

## 3. Données envoyées pour le classement

Le client envoie **les ingrédients**, pas le résultat :

```json
{
  "gameId": "…", "seed": "…", "engineVersion": "1.0.0", "saveVersion": 1,
  "options": { "sector": "restaurant", "legal": "srl", "difficulty": "realiste", "metier": null },
  "actionLog": [ { "d": 12, "a": { "type": "sector", "name": "setPrice", "value": 1250 } }, … ],
  "untilDay": 4210,
  "claimedScore": 18342
}
```

Le serveur recalcule tout (voir § 4) et ne publie que `verified_score`.
Pour le classement on affiche : pseudo, secteur, statut, difficulté, score,
années jouées, revenu passif, date ; pour la carte : ville (ou coordonnées
arrondies au km) uniquement si le joueur l'a accepté (`show_on_map`).

## 4. Anti-triche : validation par rejeu

Le moteur est déterministe : `newGame(options + seed)` puis, pour chaque jour,
appliquer les actions de ce jour (`actionLog`) et `advance(state, 1)`. Le
serveur obtient exactement l'état final du joueur et donc son score.

| Risque | Parade |
|---|---|
| Modifier sa sauvegarde (cash, score) | Le score n'est jamais lu depuis l'état envoyé : il est recalculé par rejeu. |
| Envoyer un faux journal d'actions | Le rejeu applique les mêmes règles que le jeu : une action invalide (achat sans argent…) est refusée et l'état diverge → `claimedScore ≠ verifiedScore` → run rejeté. |
| Choisir une « bonne » seed (seed farming) | Classements séparés : seed libre vs **seed du jour imposée** par le serveur (défi quotidien). Limiter le nombre de runs classés par jour. |
| Modifier le code du moteur côté client | Le serveur utilise SA version du moteur (`engineVersion` figé, hash des fichiers) ; un run joué avec une autre version est rejoué avec la version serveur correspondante ou refusé. |
| Rejeu coûteux (déni de service) | Limiter la taille de `actionLog` (déjà borné à 20 000 entrées), la durée (`untilDay` ≤ 30 ans), le nombre de soumissions par utilisateur ; file d'attente. Un rejeu de 20 ans prend ≈ 0,3 s en Node. |
| Bots qui jouent à la place de l'humain | Difficile à empêcher totalement ; afficher la durée réelle de jeu, limiter la vitesse (le jeu ne dépasse pas ×4), signalements. |
| Usurpation d'identité | Auth Google + RLS PostgreSQL (`user_id = auth.uid()`). |
| Vie privée (carte) | Opt-in explicite, coordonnées arrondies, pseudo plutôt que nom, suppression de compte (RGPD). |

Points d'attention pour que le rejeu reste fiable :
- **Les actions doivent être appliquées au même jour** : le jeu applique déjà
  chaque action immédiatement et l'enregistre avec `state.time.day` ; le
  moteur ne simule que des jours entiers, donc l'instant exact dans la journée
  n'a aucune influence.
- **Aucune source d'aléa hors du RNG à graine** dans `src/engine/` (vérifié par
  `tests/architecture.test.js` : pas de `Math.random`, pas de `Date`).
- **Flottants** : l'argent est en centimes entiers ; les autres calculs
  flottants sont identiques d'un moteur JavaScript à l'autre (IEEE 754), mais
  il faut éviter les fonctions dont la précision n'est pas garantie par la
  spécification (`Math.pow`, `Math.exp`, `Math.log` peuvent différer au dernier
  bit selon le moteur). Pour un rejeu serveur strict, exécuter le rejeu dans le
  même moteur (V8 côté client et serveur : Chrome / Node / Deno) ou remplacer
  ces fonctions par des implémentations maison.

## 5. Étapes de mise en œuvre

1. Créer le projet Supabase, activer Google OAuth, créer les tables + RLS.
2. `src/storage/CloudSaveAdapter.js` (même contrat que `LocalStorageAdapter`).
3. UI : connexion/déconnexion, choix du pseudo, emplacements « cloud ».
4. Edge Function `verify-run` (importe `src/engine/index.js`, rejoue, écrit `verified_score`).
5. Onglet Classement (filtres secteur/difficulté/statut) + défi quotidien (seed du jour).
6. Carte : Leaflet + tuiles OpenStreetMap (attribution), points agrégés par ville.
